Python Syntax Fundamentals

Classes, instances, f-strings, and control flow: the foundation everything else builds on.

Classes and Instances

Python's philosophy is that developers are trusted adults. The language gets out of your way. The tradeoff: it won't protect you from yourself.

Seven things that will feel wrong at first:

  • No type declarations — Python infers type at runtime.
  • No access modifiers — no public/private. Convention (_prefix) signals intent but the language doesn't enforce it.
  • No curly braces — indentation IS structure. A misplaced space can silently change your code.
  • No semicolons — newline ends a statement.
  • def for all methods — every function uses def regardless of return type.
  • self is explicit — every instance method declares self as its first parameter.
  • __init__ instead of a constructor — runs automatically when you create a new instance.

The class is the blueprint. The instance is a specific object built from that blueprint. Methods are functions that belong to the class and operate on a specific instance's data via self.

Why this matters: When you call the Claude API, the SDK gives you objects, instances of classes the SDK defines. Understanding that an object has properties you can access and methods you can call is what lets you navigate those objects confidently.
Exercise — Create lesson1.py

class EngagementAnalyzer:
    def __init__(self, client_name, team_size):

analyzer_2 = EngagementAnalyzer("Wayne Enterprises", 4)

print(analyzer_2.get_summary())
print(analyzer_1.client_name)   # access property directly

Data Types, Functions, and Loops

Lists, dicts, nested structures, and the patterns you'll use every time you call the API.

Lists

An ordered collection. Accessed by index starting at 0. Use -1 to get the last item without knowing the list length.

Claude API responses contain a list of content blocks. Knowing how to access items by index is how you extract text from a real API response.
lesson2.py
# --- list ---
practice_areas = ["Management Consulting", "Software Engineering", "Product & Strategy"]

print(practice_areas[0])       # 'Management Consulting'
print(practice_areas[-1])      # 'Product & Strategy' (last item)
print(len(practice_areas))     # 3
practice_areas.append('Security')
print(len(practice_areas))     # 4

Dicts

Key-value pairs. Each key must be unique within the dict. Values can be any type: strings, numbers, booleans, lists, or other dicts.

Dicts are the native shape of JSON data. Everything the Claude API sends and receives is structured as nested dicts and lists.
lesson2.py (continued)
# --- dict ---
engagement = {
    "client": "Acme Corp",
    "team_size": 15,
    "active": True
}

print(engagement["client"])             # "Acme Corp"
engagement["industry"] = "Mfg"          # add new key
engagement["team_size"] = 18            # overwrite existing key
print(engagement.get("email"))          # None — safe, no crash
print(engagement.get("email", "n/a"))  # "n/a" — with fallback

Nested Structures

Dicts and lists can contain each other. Each [] takes you one level deeper. Think of it as a path: each bracket is one step further in.

lesson2.py (continued)
response = {
    "content": [
        {"type": "text", "text": "Hello from Claude"}
    ]
}

print(response["content"])              # the list
print(response["content"][0])           # first dict in the list
print(response["content"][0]["text"])  # "Hello from Claude"
This exact pattern — response["content"][0]["text"] — is how you extract text from a plain dict representation of a Claude API response. On a real SDK response object, the equivalent is response.content[0].text using dot notation.

Keyword Arguments

Functions can be called positionally (order matters) or by keyword (names matter, order doesn't).

Every Anthropic SDK call uses keyword arguments: client.messages.create(model=..., max_tokens=..., messages=...). The parameter names matter, not the order.
python
def greet(name, greeting='Hello'):
    return f"{greeting}, {name}!"

greet("Tom", "Howdy")             # positional — order matters
greet("Tom", greeting="Howdy")    # keyword — same result

Dictionary Unpacking with **

The ** operator unpacks a dictionary into keyword arguments. Instead of writing out every parameter in a function call, you build a dict, conditionally add to it, then unpack it with **.

python
# Without ** — every parameter written out every time
client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1000,
    messages=messages,
    temperature=1.0
)

# With ** — build the dict first, unpack it into the call
params = {
    "model": model,
    "max_tokens": 1000,
    "messages": messages,
    "temperature": temperature
}

if system:
    params["system"] = system       # only added when needed

if stop_sequences:
    params["stop_sequences"] = stop_sequences

client.messages.create(**params)   # unpacks dict as keyword arguments
Why the chat() helper in the Skilljar course uses this pattern: system and stop_sequences should only be sent when they have values. Building the dict conditionally and unpacking it is cleaner than writing multiple versions of the function call. You will see **params any time a function call has optional parameters that vary by context.

JSON in Python

The explicit certification prerequisite. Everything the Claude API sends and receives travels as JSON.

The Four Functions

The s suffix means string. No s means file. That's the only distinction to memorize.

FunctionWhat it does
json.dumps(obj)Python dict → JSON string
json.loads(str)JSON string → Python dict
json.dump(obj, f)Python dict → JSON file
json.load(f)JSON file → Python dict
lesson4.py
import json

engagement = {'client': 'Acme Corp', 'active': True, 'findings': ["Process gaps", "Legacy tech"]}

# Dict → string
json_string = json.dumps(engagement)
print(type(json_string))    # <class 'str'>

# String → dict
parsed = json.loads(json_string)
print(type(parsed))         # <class 'dict'>
print(parsed["client"])     # Acme Corp

# Human-readable formatting
print(json.dumps(engagement, indent=2))

# Dict → file
with open("engagement.json", "w") as f:
    json.dump(engagement, f, indent=2)

# File → dict
with open("engagement.json", "r") as f:
    loaded = json.load(f)
print(loaded["findings"])
First debugging move: when a Claude API response looks wrong, always run print(json.dumps(response, indent=2)) to see its full structure.

Testing with pytest

TDD discipline that lets you move fast without breaking things.

The Pattern

  1. Write a failing test that reflects a feature requirement. A test that cannot fail cannot prove anything.
  2. Write enough code to pass the test. No more.
  3. Refactor with your tests as a safety net.

Conventions pytest Relies On

  • File naming: test_*.py — pytest won't find files that don't match this pattern
  • Function naming: starts with test_
  • Assertions: use assert — if it fails, the test fails
  • One thing per test: if the first assert fails, the rest don't run
CommandWhat it does
pytestRun all tests in the project — auto-discovers test_*.py files
pytest -vVerbose — shows each test by name with PASSED or FAILED
pytest test_lesson3.pyRun one specific file
pytest test_lesson3.py -vSpecific file, verbose

Testing LLM Output — Assert Loosely

Every assert you've seen so far tests a deterministic function: same input, same output, so exact-match assertions are correct. Claude's responses are nondeterministic — ask the same question twice and you get the same idea in different words. A test that asserts exact phrasing will pass one day and fail the next, even though nothing is broken.

This happened in this course's own test suite. The first assertion below originally checked for the literal phrase "Python list". It passed for weeks — until Claude phrased its answer as "A list is an ordered, mutable collection…" without ever using those two words together. The code was fine; the test was brittle. The fix: assert on the topic keyword, case-insensitively.

test_lesson5.py
from lesson5 import chat

def test_chat():
    response1 = chat("What is a Python list?")
    assert "list" in response1.lower()   # topic keyword, not exact phrasing

    response2 = chat("How is it different from a tuple?")
    assert "tuple" in response2
  • Assert on topic keywords, lowercased: "list" in response.lower() survives any phrasing of a correct answer
  • Assert on structure when you control the format: if you asked for JSON, json.loads() the response and check the keys exist — not the values' wording
  • Never assert exact sentences or phrases against an LLM response — you are testing the model's word choice, not your code
Why this matters: a brittle test that fails on correct behavior trains you to ignore failures — the most expensive habit a test suite can teach. Tests on LLM output should ask "did the response cover the right thing?" (keywords, structure, type), never "did it say it the way I expected?"

Common Gotchas: Know Before Module 4

Seven patterns that trip up developers working with the Anthropic API.

1. dict["key"] Crashes — dict.get() Does Not

python
user["email"]                    # KeyError if key missing — crashes
user.get("email")                # None — safe
user.get("email", "no email")   # "no email" — with fallback
API responses often have optional fields. Always use .get() when you are not certain a key exists.

2. SDK Objects Use Dot Notation, Not Brackets

python
response["content"][0]["text"]   # plain dict — bracket notation
response.content[0].text         # SDK object — dot notation

# Convert SDK object to plain dict if needed:
response_dict = response.model_dump()

3. Always Check stop_reason

ValueMeaning
"end_turn"Claude finished naturally. Most common.
"max_tokens"Response was cut off. Increase max_tokens and retry.
"tool_use"Claude wants to call a tool. Handle in the tool-use loop.
"stop_sequence"Hit a custom stop sequence. Uncommon.
Never assume a response is complete just because content[0].text has a value. If stop_reason is "max_tokens", the response was cut off mid-sentence.

4. Token Usage — How Billing Works

python
response.usage.input_tokens    # tokens in your request
response.usage.output_tokens   # tokens in Claude's response

Output tokens are billed at a higher rate than input tokens. The system prompt counts as input tokens on every single call.

5. content Is Always a List

python
response.content              # list of content blocks — never use directly
response.content[0]           # first block
response.content[0].text      # the text string
Even when Claude returns a single sentence, content is a list. You always need [0].

6. = vs ==

python
stop_reason = 'end_turn'        # assigns — sets the variable
stop_reason == 'end_turn'       # compares — returns True or False
if stop_reason == 'end_turn':   # correct conditional check

7. Model Strings Change Over Time

Never memorize a snapshot. Verify against current documentation. Current models:

ModelUse case
claude-opus-4-6Highest capability, highest cost
claude-sonnet-4-6Default workhorse — strong quality, mid cost
claude-haiku-4-5-20251001Fastest, cheapest, lightest tasks
Start with Sonnet. Escalate to Opus if quality is insufficient. Drop to Haiku if speed or cost is the constraint.

The System Prompt

Sets Claude's persistent role, behavior, and constraints for the entire session. It is a separate parameter from messages — not a turn in the conversation. Sent with every API call and counts as input tokens each time.

python
SYSTEM_PROMPT = """You are an AI assistant for [Your Firm].
Apply systems thinking to client problems.
Keep responses concise and actionable."""

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    system=SYSTEM_PROMPT,
    messages=messages
)
The system prompt is where your firm's IP lives: your frameworks, methodology, and approach. A well-crafted system prompt is what makes a generic AI model behave like your firm's analyst.

Multi-Turn Conversations

Claude has no memory between API calls. Every call is stateless. To maintain a conversation, pass the full message history on every call, appending both your messages and Claude's responses to the same list.

lesson5.py — multi-turn pattern
messages = []

def chat(user_message):
    messages.append({"role": "user", "content": user_message})

    response = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=1024,
        system=SYSTEM_PROMPT,
        messages=messages
    )

    assistant_message = response.content[0].text
    messages.append({"role": "assistant", "content": assistant_message})
    return assistant_message

The conversation shape — roles must alternate user → assistant → user → assistant:

python
messages = [
    {"role": "user",      "content": "What is a Python list?"},
    {"role": "assistant", "content": "A Python list is..."},
    {"role": "user",      "content": "How is it different from a tuple?"},
]
Roles must alternate. You cannot send two user messages in a row. Claude cannot send two assistant messages in a row. Violating this causes a BadRequestError.

Prompt Caching

Without caching, the system prompt is billed as full input tokens on every single call. Adding cache_control marks the system prompt as cacheable; subsequent calls that send the same content pay a reduced rate.

consulting_assistant.py
from anthropic import Anthropic
from dotenv import load_dotenv

load_dotenv()
client = Anthropic()

SYSTEM_PROMPT = """You are an AI assistant for [Your Firm], a management consulting firm.

Your role is to help consultants think through client problems with rigor and clarity.
You apply systems thinking and domain-driven approaches to analysis.
Keep responses concise and structured. Avoid generic advice — be specific and actionable."""

messages = []

def chat(user_message):
    messages.append({"role": "user", "content": user_message})

    response = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=4096,
        system=[{"type": "text", "text": SYSTEM_PROMPT, "cache_control": {"type": "ephemeral"}}],
        messages=messages,
    )

    assistant_message = response.content[0].text
    messages.append({"role": "assistant", "content": assistant_message})
    return assistant_message

if __name__ == "__main__":
    print(chat("A client's order fulfillment process has a 3-day cycle time. Their competitor is at 1 day. Where do I start?"))
if __name__ == "__main__": This guard means the print(chat(...)) line only runs when the file is executed directly (python consulting_assistant.py), not when it is imported by pytest. Without it, every test run triggers a live API call at import time.

Claude Code CLI

Non-interactive mode and CI/CD pipeline patterns: a specific scenario on the CCA-F exam.

The -p Flag

claude -p "query" runs Claude Code in non-interactive mode. It processes the prompt, outputs the result to stdout, and exits. A pipeline without -p hangs waiting for input.

Exam trap: one question gives four options for fixing a hanging pipeline job — CLAUDE_HEADLESS=true (not a real flag), stdin redirect from /dev/null (a hack, not the answer), --batch (not a valid flag), and -p (correct).
terminal
# One-shot query — runs and exits
claude -p "What does this function do?"

# Pipe file contents as context
cat lesson5.py | claude -p "Review this file for issues"

# Pipe git diff for code review
git diff | claude -p "Summarize what changed in plain English"

# Get structured JSON output
cat lesson5.py | claude -p "Review for issues" --output-format json

# Prevent runaway agentic loops
claude -p "Fix the failing tests" --max-turns 5

JSON Output Structure

When using --output-format json, the response contains:

CI/CD Pipeline Patterns

permission modes
# Default — safest, prompts for confirmation on file edits
claude -p "query"

# Auto-accept edits — semi-automated
claude -p "query" --permission-mode acceptEdits

# Bypass all permissions — sandboxed CI only
claude -p "query" --permission-mode bypassPermissions
Use bypassPermissions only in sandboxed CI environments. It drops all safety instructions; you take full responsibility for what Claude can do.
GitHub Actions example
# In a GitHub Actions workflow YAML:
- name: Claude code review
  run: |
    git diff origin/main | claude -p "Review for bugs and security issues" \
      --output-format json \
      --max-turns 3

Coordinator-Subagent Model Selection

Claude Code automatically uses multiple models. Haiku handles lightweight orchestration decisions (routing, planning, "what tool next?"). Sonnet does the substantive work. You don't configure this; Claude Code selects based on task complexity. You'll see both in modelUsage in JSON output.

Session context isolation (exam topic): the same Claude instance that generated code will rationalize its own decisions during review. An independent instance without generation context catches more bugs. In CI/CD, always use a fresh session for review steps — don't reuse the generation session.

Course Corrections

Corrected patterns, content gaps, and known issues in the Skilljar course notebooks.

Structured Output: Prefill → output_config

Breaking change in Claude 4.6+: The Skilljar course "Building with the Claude API" teaches assistant message prefill as a structured output technique. This no longer works on Sonnet or Opus. Haiku remains more permissive and may still accept trailing assistant messages, but this behavior is not guaranteed across API updates and should not be relied on in production. Any request with a trailing assistant message on Sonnet or Opus returns:

BadRequestError: 400 — This model does not support assistant message prefill. The conversation must end with a user message.

The course exercise that does still work is stop sequences — stop_sequences=["5", "3, 4"] is valid on all current models and needs no changes.

Why Prefill Was a Workaround

The problem prefill solved: when asked to extract data as JSON, Claude responds conversationally — preamble, the JSON, postamble. Prefill exploited the messages array by ending with a fake assistant turn containing '{', causing Claude to continue from that point and produce only the JSON body. It worked, but it was fragile (Claude might still add text after the closing brace), semantically wrong (injecting a fake conversation turn), and caused subtle issues in multi-turn conversations where the fake turn became part of Claude's reasoning history.

The exam meta-principle: programmatic enforcement is almost always preferred over prompt-based guidance. Prefill was prompt manipulation — nudging behavior. output_config is programmatic enforcement — constraining the sampling process at the model level. When the exam asks how to guarantee structured output, the correct answer is always schema-constrained output. Prefill may appear as a distractor in answer choices.

The Modern Replacement: output_config

Anthropic's replacement for prefill-based structured output is output_config with a JSON schema. This constrains Claude at the model level to return only valid JSON matching your schema: no preamble, no markdown fences, no explanation.

python
import json
from anthropic import Anthropic

client = Anthropic()

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1000,

Arrays of Objects: Nested Schema Pattern

When a field contains a list of structured items — each with multiple properties — use an array of objects. Each item in the array is itself an object with its own properties and required fields.

python — nested array schema
"kpis": {
    "type": "array",
    "items": {
        "type": "object",
        "properties": {
            "current": {"type": "string"},
            "target":  {"type": "string"}
        },
        "required": ["current", "target"],
        "additionalProperties": False
    }
}
additionalProperties: False applies to every object in the schema, including nested objects inside array items. Omitting it on a nested object causes a 400 error even if the top-level object has it set correctly.

A full working example using this pattern is in consulting_notes_extractor.py. It extracts structured findings (client, priority, actions, problems, KPIs) from unstructured meeting notes and includes six tests in test_consulting_notes_extractor.py. The original course notebook is preserved as 004_structured_output.ipynb.

Prompt Evaluation — generate_dataset and grade_by_model Prefill → output_config

Second instance of this pattern: The Skilljar "Building with the Claude API" course notebook 001_prompt_evals.ipynb uses the same deprecated prefill technique in both generate_dataset and grade_by_model: wrapping a response in a ```json code fence and cutting it off with a stop sequence. This fails on Sonnet and Opus for the same reason: the API no longer accepts a trailing assistant message on those models.

The deprecated pattern from the course:

deprecated — do not use 
# Broken on Sonnet and Opus — prefill hack
messages = []
add_user_message(messages, prompt)
add_assistant_message(messages, "```json")   # fake assistant turn
text = chat(messages, stop_sequences=["```"])    # cut before closing fence
return json.loads(text)

The output_config Replacement

The corrected generate_dataset function uses output_config directly in the client.messages.create() call. Note that the schema top-level type is "array", not "object" — the API returns a list of task objects rather than a single object. Arrays can be the top-level schema type when your output is inherently a collection.

generate_dataset — corrected 
import json

def generate_dataset():
    prompt = """
Generate 3 evaluation tasks for prompts that produce Python, JSON, or Regex
for AWS-related use cases. Each task should be solvable with a single function,
object, or expression.
"""
    response = client.messages.create(
        model="claude-haiku-4-5",
        max_tokens=1000,
        messages=[{"role": "user", "content": prompt}],
        output_config={
            "format": {
                "type": "json_schema",
                "schema": {
                    "type": "array",           # top-level is a list, not an object
                    "items": {
                        "type": "object",
                        "properties": {
                            "task": {"type": "string"}
                        },
                        "required": ["task"],
                        "additionalProperties": False
                    }
                }
            }
        }
    )
    return json.loads(response.content[0].text)
Where output_config belongs: output_config goes in the specific client.messages.create() call where structured JSON is needed — not in a general-purpose chat() helper. The chat() helper stays generic. Only the function that contracts with the API for a particular shape carries output_config. This is the same pattern used in consulting_notes_extractor.py.
Why the grader notebook may still run: The supplied 001_prompt_evals_grader.ipynb uses claude-haiku-4-5, which remains more permissive about trailing assistant messages than Sonnet or Opus. The notebook may run successfully as provided. This is not a reason to keep the pattern — Haiku's permissiveness is not guaranteed across API updates. Use output_config for any structured output that needs to be stable.

The repo preserves the corrected notebook as 001_prompt_evals.ipynb.

Text Editor Tool — Tool Name Mismatch

Course notebook bug — infinite loop: The Skilljar "Tool Use with Claude" course notebook 005_text_editor_tool.ipynb dispatches tool calls using the deprecated tool name "str_replace_editor" in run_tool, but registers the tool with the current name "str_replace_based_edit_tool" in get_text_edit_schema. These names never match. Every tool call returns is_error: True, Claude retries, and the while True loop never breaks — the kernel appears stuck and the cell must be interrupted manually.

The mismatch in the original notebook:

cell 3 — deprecated, do not use 
# run_tool dispatches on the old name — never matches
if tool_name == "str_replace_editor":   # ← wrong

# cell 4 registers the tool with the current name
"name": "str_replace_based_edit_tool"   # ← what Claude actually calls

The Fix

Update the if condition in run_tool to match the name the API actually uses for text_editor_20250728. The tool name is fixed by Anthropic and cannot be changed.

cell 3 — corrected 
def run_tool(tool_name, tool_input):
    if tool_name == "str_replace_based_edit_tool":   # matches the registered name
        command = tool_input["command"]
        # ... rest of dispatch unchanged
Why the loop hangs: When run_tool raises an exception, run_tools catches it and returns a tool_result block with is_error: True. Claude receives the error, says "let me try again," and calls the same tool — which fails again. Because stop_reason stays "tool_use", the while True loop never reaches its break condition. The fix is the same principle as always: the name in your dispatch must exactly match the name Claude uses when calling the tool.

The notebook also used the deprecated model string claude-sonnet-4-5. Update to claude-sonnet-4-6. The corrected notebook is preserved as 005_text_editor_tool.ipynb in the repo.

Web Search Tool — Demo Question Produces No Search

Content gap — no error, but the lesson does not demonstrate what it claims: The Skilljar "Tool Use with Claude" course notebook 006_web_search_complete.ipynb asks "What's the best exercise for gaining leg muscle?" This is stable knowledge Claude answers from training data. No web search fires. The ServerToolUseBlock and WebSearchToolResultBlock response structure the lesson exists to demonstrate never appears in the output.

Claude decides whether to search based on whether the question requires current information. Stable knowledge questions — best practices, definitions, general advice — are answered from training data regardless of whether a search tool is registered. The fix is to ask a question that signals recency.

cell 4 — original, produces no search 
# Claude answers from training data — no ServerToolUseBlock in response
add_user_message(messages, "What's the best exercise for gaining leg muscle?")
cell 4 — corrected, forces a live search 
# "latest" signals recency — Claude searches rather than answering from memory
# allowed_domains: ["nih.gov"] already in the schema, so the search stays scoped
add_user_message(messages, """
    What are the latest NIH recommendations on exercise for cardiovascular health?
""")
What the full response looks like when a search fires: The response content array contains a ServerToolUseBlock (showing the query Claude used), a WebSearchToolResultBlock (the search results), and a final TextBlock (Claude's answer with citations). The server_tool_use field in response.usage will show a non-zero web_search_requests count. If you only see a single TextBlock and server_tool_use: None, no search fired — rephrase the question to require current information.

The notebook also used the deprecated model string claude-sonnet-4-5. Update to claude-sonnet-4-6. The corrected notebook is preserved as 006_web_search_complete.ipynb in the repo.

Extended Thinking — budget_tokens → Adaptive Thinking

Deprecated API pattern: The Skilljar "Features of Claude" course notebook 001_thinking_complete.ipynb uses thinking={"type": "enabled", "budget_tokens": N} — the fixed token budget thinking API. This is deprecated on Sonnet 4.6 and Opus 4.6, and removed entirely on Opus 4.7 and later. Requests using type: "enabled" on Opus 4.7+ return a 400 error. The RedactedThinkingBlock the notebook was designed to demonstrate no longer exists as a discrete block type on current models.

The deprecated pattern from the course:

deprecated — do not use on 4.6+ 
# Broken on Opus 4.7+ — returns 400 error
# Deprecated on Sonnet/Opus 4.6
params["thinking"] = {
    "type": "enabled",
    "budget_tokens": thinking_budget,   # fixed token budget — removed
}

The Adaptive Thinking Replacement

Adaptive thinking replaces the fixed token budget with an effort level. Claude decides if and when to think based on problem complexity — a simple question may produce no thinking block at all. Use a genuinely complex problem to reliably observe a ThinkingBlock in the response.

corrected — adaptive thinking 
# Adaptive thinking: Claude decides when to think based on complexity
# effort: "low" | "medium" | "high" | "max"
params["thinking"] = {
    "type": "adaptive",
    "effort": "high",
}

# Extract thinking content from the response
for block in response.content:
    if block.type == "thinking":
        print(block.thinking)   # ThinkingBlock — not RedactedThinkingBlock
Why RedactedThinkingBlock no longer appears: RedactedThinkingBlock was produced by the old type: "enabled" API when Claude's reasoning was withheld for safety reasons. The adaptive thinking API replaced this entirely. With type: "adaptive", Claude either produces a ThinkingBlock with summarized reasoning or produces no thinking block at all. There is no equivalent to RedactedThinkingBlock in the current API.
