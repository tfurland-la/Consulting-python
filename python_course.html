Python Syntax Fundamentals

Classes, instances, f-strings, and control flow: the foundation everything else builds on.

Classes and Instances

Python's philosophy is that developers are trusted adults. The language gets out of your way. The tradeoff: it won't protect you from yourself.

Seven things that will feel wrong at first:

  • No type declarations — Python infers type at runtime.
  • No access modifiers — no public/private. Convention (_prefix) signals intent but the language doesn't enforce it.
  • No curly braces — indentation IS structure. A misplaced space can silently change your code.
  • No semicolons — newline ends a statement.
  • def for all methods — every function uses def regardless of return type.
  • self is explicit — every instance method declares self as its first parameter.
  • __init__ instead of a constructor — runs automatically when you create a new instance.

The class is the blueprint. The instance is a specific object built from that blueprint. Methods are functions that belong to the class and operate on a specific instance's data via self.

Why this matters: When you call the Claude API, the SDK gives you objects, instances of classes the SDK defines. Understanding that an object has properties you can access and methods you can call is what lets you navigate those objects confidently.

class EngagementAnalyzer:
    def __init__(self, client_name, team_size):

analyzer_2 = EngagementAnalyzer("Wayne Enterprises", 4)

print(analyzer_2.get_summary())
print(analyzer_1.client_name)   # access property directly

Data Types, Functions, and Loops

Lists, dicts, nested structures, and the patterns you'll use every time you call the API.

Lists

An ordered collection. Accessed by index starting at 0. Use -1 to get the last item without knowing the list length.

Claude API responses contain a list of content blocks. Knowing how to access items by index is how you extract text from a real API response.
lesson2.py
# --- list ---
practice_areas = ["Management Consulting", "Software Engineering", "Product & Strategy"]

print(practice_areas[0])       # 'Management Consulting'
print(practice_areas[-1])      # 'Product & Strategy' (last item)
print(len(practice_areas))     # 3
practice_areas.append('Security')
print(len(practice_areas))     # 4

Dicts

Key-value pairs. Each key must be unique within the dict. Values can be any type: strings, numbers, booleans, lists, or other dicts.

Dicts are the native shape of JSON data. Everything the Claude API sends and receives is structured as nested dicts and lists.
lesson2.py (continued)
# --- dict ---
engagement = {
    "client": "Acme Corp",
    "team_size": 15,
    "active": True
}

print(engagement["client"])             # "Acme Corp"
engagement["industry"] = "Mfg"          # add new key
engagement["team_size"] = 18            # overwrite existing key
print(engagement.get("email"))          # None — safe, no crash
print(engagement.get("email", "n/a"))  # "n/a" — with fallback

Nested Structures

Dicts and lists can contain each other. Each [] takes you one level deeper. Think of it as a path: each bracket is one step further in.

lesson2.py (continued)
response = {
    "content": [
        {"type": "text", "text": "Hello from Claude"}
    ]
}

print(response["content"])              # the list
print(response["content"][0])           # first dict in the list
print(response["content"][0]["text"])  # "Hello from Claude"
This exact pattern — response["content"][0]["text"] — is how you extract text from a plain dict representation of a Claude API response. On a real SDK response object, the equivalent is response.content[0].text using dot notation.

Keyword Arguments

Functions can be called positionally (order matters) or by keyword (names matter, order doesn't).

Every Anthropic SDK call uses keyword arguments: client.messages.create(model=..., max_tokens=..., messages=...). The parameter names matter, not the order.
python
def greet(name, greeting='Hello'):
    return f"{greeting}, {name}!"

greet("Tom", "Howdy")             # positional — order matters
greet("Tom", greeting="Howdy")    # keyword — same result

Dictionary Unpacking with **

The ** operator unpacks a dictionary into keyword arguments. Instead of writing out every parameter in a function call, you build a dict, conditionally add to it, then unpack it with **.

python
# Without ** — every parameter written out every time
client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1000,
    messages=messages,
    temperature=1.0
)

# With ** — build the dict first, unpack it into the call
params = {
    "model": model,
    "max_tokens": 1000,
    "messages": messages,
    "temperature": temperature
}

if system:
    params["system"] = system       # only added when needed

if stop_sequences:
    params["stop_sequences"] = stop_sequences

client.messages.create(**params)   # unpacks dict as keyword arguments
Why the chat() helper in the Skilljar course uses this pattern: system and stop_sequences should only be sent when they have values. Building the dict conditionally and unpacking it is cleaner than writing multiple versions of the function call. You will see **params any time a function call has optional parameters that vary by context.

JSON in Python

The explicit certification prerequisite. Everything the Claude API sends and receives travels as JSON.

The Four Functions

The s suffix means string. No s means file. That's the only distinction to memorize.

FunctionWhat it does
json.dumps(obj)Python dict → JSON string
json.loads(str)JSON string → Python dict
json.dump(obj, f)Python dict → JSON file
json.load(f)JSON file → Python dict
lesson4.py
import json

engagement = {'client': 'Acme Corp', 'active': True, 'findings': ["Process gaps", "Legacy tech"]}

# Dict → string
json_string = json.dumps(engagement)
print(type(json_string))    # <class 'str'>

# String → dict
parsed = json.loads(json_string)
print(type(parsed))         # <class 'dict'>
print(parsed["client"])     # Acme Corp

# Human-readable formatting
print(json.dumps(engagement, indent=2))

# Dict → file
with open("engagement.json", "w") as f:
    json.dump(engagement, f, indent=2)

# File → dict
with open("engagement.json", "r") as f:
    loaded = json.load(f)
print(loaded["findings"])
First debugging move: when a Claude API response looks wrong, always run print(json.dumps(response, indent=2)) to see its full structure.

Testing with pytest

TDD discipline that lets you move fast without breaking things.

The Pattern

  1. Write a failing test that reflects a feature requirement. A test that cannot fail cannot prove anything.
  2. Write enough code to pass the test. No more.
  3. Refactor with your tests as a safety net.

Conventions pytest Relies On

  • File naming: test_*.py — pytest won't find files that don't match this pattern
  • Function naming: starts with test_
  • Assertions: use assert — if it fails, the test fails
  • One thing per test: if the first assert fails, the rest don't run
CommandWhat it does
pytestRun all tests in the project — auto-discovers test_*.py files
pytest -vVerbose — shows each test by name with PASSED or FAILED
pytest test_lesson3.pyRun one specific file
pytest test_lesson3.py -vSpecific file, verbose

Testing LLM Output — Assert Loosely

Every assert you've seen so far tests a deterministic function: same input, same output, so exact-match assertions are correct. Claude's responses are nondeterministic — ask the same question twice and you get the same idea in different words. A test that asserts exact phrasing will pass one day and fail the next, even though nothing is broken.

This happened in this course's own test suite. The first assertion below originally checked for the literal phrase "Python list". It passed for weeks — until Claude phrased its answer as "A list is an ordered, mutable collection…" without ever using those two words together. The code was fine; the test was brittle. The fix: assert on the topic keyword, case-insensitively.

test_lesson5.py
from lesson5 import chat

def test_chat():
    response1 = chat("What is a Python list?")
    assert "list" in response1.lower()   # topic keyword, not exact phrasing

    response2 = chat("How is it different from a tuple?")
    assert "tuple" in response2
  • Assert on topic keywords, lowercased: "list" in response.lower() survives any phrasing of a correct answer
  • Assert on structure when you control the format: if you asked for JSON, json.loads() the response and check the keys exist — not the values' wording
  • Never assert exact sentences or phrases against an LLM response — you are testing the model's word choice, not your code
Why this matters: a brittle test that fails on correct behavior trains you to ignore failures — the most expensive habit a test suite can teach. Tests on LLM output should ask "did the response cover the right thing?" (keywords, structure, type), never "did it say it the way I expected?"

Common Gotchas: Know Before Module 4

Seven patterns that trip up developers working with the Anthropic API.

1. dict["key"] Crashes — dict.get() Does Not

python
user["email"]                    # KeyError if key missing — crashes
user.get("email")                # None — safe
user.get("email", "no email")   # "no email" — with fallback
API responses often have optional fields. Always use .get() when you are not certain a key exists.

2. SDK Objects Use Dot Notation, Not Brackets

python
response["content"][0]["text"]   # plain dict — bracket notation
response.content[0].text         # SDK object — dot notation

# Convert SDK object to plain dict if needed:
response_dict = response.model_dump()

3. Always Check stop_reason

ValueMeaning
"end_turn"Claude finished naturally. Most common.
"max_tokens"Response was cut off. Increase max_tokens and retry.
"tool_use"Claude wants to call a tool. Handle in the tool-use loop.
"stop_sequence"Hit a custom stop sequence. Uncommon.
Never assume a response is complete just because content[0].text has a value. If stop_reason is "max_tokens", the response was cut off mid-sentence.

4. Token Usage — How Billing Works

python
response.usage.input_tokens    # tokens in your request
response.usage.output_tokens   # tokens in Claude's response

Output tokens are billed at a higher rate than input tokens. The system prompt counts as input tokens on every single call.

5. content Is Always a List

python
response.content              # list of content blocks — never use directly
response.content[0]           # first block
response.content[0].text      # the text string
Even when Claude returns a single sentence, content is a list. You always need [0].

6. = vs ==

python
stop_reason = 'end_turn'        # assigns — sets the variable
stop_reason == 'end_turn'       # compares — returns True or False
if stop_reason == 'end_turn':   # correct conditional check

7. Model Strings Change Over Time

Never memorize a snapshot. Verify against current documentation. Current models:

ModelUse case
claude-opus-4-6Highest capability, highest cost
claude-sonnet-4-6Default workhorse — strong quality, mid cost
claude-haiku-4-5-20251001Fastest, cheapest, lightest tasks
Start with Sonnet. Escalate to Opus if quality is insufficient. Drop to Haiku if speed or cost is the constraint.

Setup and First API Call

The System Prompt

Sets Claude's persistent role, behavior, and constraints for the entire session. It is a separate parameter from messages — not a turn in the conversation. Sent with every API call and counts as input tokens each time.

python
SYSTEM_PROMPT = """You are an AI assistant for [Your Firm].
Apply systems thinking to client problems.
Keep responses concise and actionable."""

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    system=SYSTEM_PROMPT,
    messages=messages
)
The system prompt is where your firm's IP lives: your frameworks, methodology, and approach. A well-crafted system prompt is what makes a generic AI model behave like your firm's analyst.

Multi-Turn Conversations

Claude has no memory between API calls. Every call is stateless. To maintain a conversation, pass the full message history on every call, appending both your messages and Claude's responses to the same list.

lesson5.py — multi-turn pattern
messages = []

def chat(user_message):
    messages.append({"role": "user", "content": user_message})

    response = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=1024,
        system=SYSTEM_PROMPT,
        messages=messages
    )

    assistant_message = response.content[0].text
    messages.append({"role": "assistant", "content": assistant_message})
    return assistant_message

The conversation shape — roles must alternate user → assistant → user → assistant:

python
messages = [
    {"role": "user",      "content": "What is a Python list?"},
    {"role": "assistant", "content": "A Python list is..."},
    {"role": "user",      "content": "How is it different from a tuple?"},
]
Roles must alternate. You cannot send two user messages in a row. Claude cannot send two assistant messages in a row. Violating this causes a BadRequestError.

Prompt Caching

Without caching, the system prompt is billed as full input tokens on every single call. Adding cache_control marks the system prompt as cacheable; subsequent calls that send the same content pay a reduced rate.

consulting_assistant.py
from anthropic import Anthropic
from dotenv import load_dotenv

load_dotenv()
client = Anthropic()

SYSTEM_PROMPT = """You are an AI assistant for [Your Firm], a management consulting firm.

Your role is to help consultants think through client problems with rigor and clarity.
You apply systems thinking and domain-driven approaches to analysis.
Keep responses concise and structured. Avoid generic advice — be specific and actionable."""

messages = []

def chat(user_message):
    messages.append({"role": "user", "content": user_message})

    response = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=4096,
        system=[{"type": "text", "text": SYSTEM_PROMPT, "cache_control": {"type": "ephemeral"}}],
        messages=messages,
    )

    assistant_message = response.content[0].text
    messages.append({"role": "assistant", "content": assistant_message})
    return assistant_message

if __name__ == "__main__":
    print(chat("A client's order fulfillment process has a 3-day cycle time. Their competitor is at 1 day. Where do I start?"))
if __name__ == "__main__": This guard means the print(chat(...)) line only runs when the file is executed directly (python consulting_assistant.py), not when it is imported by pytest. Without it, every test run triggers a live API call at import time.

Claude Code CLI

Non-interactive mode and CI/CD pipeline patterns: a specific scenario on the CCA-F exam.

The -p Flag

claude -p "query" runs Claude Code in non-interactive mode. It processes the prompt, outputs the result to stdout, and exits. A pipeline without -p hangs waiting for input.

Exam trap: one question gives four options for fixing a hanging pipeline job — CLAUDE_HEADLESS=true (not a real flag), stdin redirect from /dev/null (a hack, not the answer), --batch (not a valid flag), and -p (correct).
terminal
# One-shot query — runs and exits
claude -p "What does this function do?"

# Pipe file contents as context
cat lesson5.py | claude -p "Review this file for issues"

# Pipe git diff for code review
git diff | claude -p "Summarize what changed in plain English"

# Get structured JSON output
cat lesson5.py | claude -p "Review for issues" --output-format json

# Prevent runaway agentic loops
claude -p "Fix the failing tests" --max-turns 5

JSON Output Structure

When using --output-format json, the response contains:

CI/CD Pipeline Patterns

permission modes
# Default — safest, prompts for confirmation on file edits
claude -p "query"

# Auto-accept edits — semi-automated
claude -p "query" --permission-mode acceptEdits

# Bypass all permissions — sandboxed CI only
claude -p "query" --permission-mode bypassPermissions
Use bypassPermissions only in sandboxed CI environments. It drops all safety instructions; you take full responsibility for what Claude can do.
GitHub Actions example
# In a GitHub Actions workflow YAML:
- name: Claude code review
  run: |
    git diff origin/main | claude -p "Review for bugs and security issues" \
      --output-format json \
      --max-turns 3

Coordinator-Subagent Model Selection

Claude Code automatically uses multiple models. Haiku handles lightweight orchestration decisions (routing, planning, "what tool next?"). Sonnet does the substantive work. You don't configure this; Claude Code selects based on task complexity. You'll see both in modelUsage in JSON output.

Session context isolation (exam topic): the same Claude instance that generated code will rationalize its own decisions during review. An independent instance without generation context catches more bugs. In CI/CD, always use a fresh session for review steps — don't reuse the generation session.

CLAUDE.md — Advanced Configuration

The Skilljar course covered CLAUDE.md basics: project-level, local, and user-level files. The exam tests three additional features that weren't in the course.

@import for Modular Configuration

Large CLAUDE.md files become hard to maintain. The @import syntax lets you reference external files, keeping each file focused on one concern:

CLAUDE.md — modular imports
# Root CLAUDE.md imports topic-specific files
@import .claude/standards/testing.md
@import .claude/standards/api-conventions.md
@import .claude/standards/deployment.md

.claude/rules/ for Path-Scoped Rules

Some conventions only apply to certain file types — test files, API handlers, Terraform configs. Rather than including all conventions in every context, .claude/rules/ files load only when Claude is editing files that match their glob pattern.

.claude/rules/testing.md — YAML frontmatter
---
paths:
  - "**/*.test.tsx"
  - "**/*.spec.ts"
---

# Testing conventions
All tests use the Arrange-Act-Assert pattern.
Mock external dependencies at the module boundary.
Test file names must match the component they test.

This loads only when Claude is working with test files — it never consumes context window during unrelated tasks. This is the correct answer when conventions need to apply to files spread across the codebase (e.g., test files colocated with source files in many directories), because a directory-level CLAUDE.md can't do that.

Exam question pattern: a codebase has React components, API handlers, and database models in different directories, plus test files spread throughout. Plan Mode vs Direct Execution (D3.4)

Claude Code has two operating modes. In direct execution mode (the default), Claude reads, edits, and runs files as it works. In plan mode, Claude explores and designs without making any changes — it produces a plan for your review before touching anything.

Decision Criteria

Use plan mode when…Use direct execution when…
The task spans dozens of files or servicesThe task is confined to one or two files
Multiple valid architectural approaches existThe stack trace points clearly to the fix
You're in an unfamiliar codebaseThe requirement is well-scoped and unambiguous
Incorrect implementation would be costly to undoThe change is easily reversible

The cost of skipping plan mode is rework: if implementation reveals that the architecture was wrong, you undo and restart. The cost of unnecessary plan mode is latency — so single-file fixes and clear stack traces don't warrant it.

The Explore Subagent Pattern

For large codebases, the discovery phase itself generates verbose output (directory listings, grep results, file reads) that consumes context you'll need for implementation. The solution: run discovery as an Explore subagent — it searches in its own context window and returns a structured summary. Then implement in plan mode or direct execution with that summary as your starting point rather than raw file dumps.

Combined approach: use an Explore subagent for discovery → plan mode for architectural design → direct execution for implementation. Each phase uses the right mode; none bleeds into the next.
Exam question pattern: a team is migrating a monolithic application to microservices, touching dozens of files with multiple valid service boundary options. The correct answer is plan mode — not direct execution (risks costly rework), not direct execution with upfront instructions (assumes structure you haven't explored), and not switching to plan mode only if complexity emerges (the complexity is already known from the requirements).

The Tool Use Loop

The agentic loop pattern that underlies every tool-using Claude application — and 27% of the CCA-F exam.

How the Loop Works

When Claude has access to tools, a single API call is rarely enough. Claude reasons about what it needs, requests a tool call, receives the result, and reasons again. This cycle continues until Claude has enough information to give a final answer. The structure that drives this is called the agentic loop.

The loop has four steps that repeat:

  • Send a request to Claude with available tool schemas
  • Check stop_reason — if "tool_use", Claude wants to call a tool
  • Execute the requested tool and append the result to conversation history
  • Send the updated history back to Claude and repeat

The loop terminates when stop_reason is "end_turn" — Claude has finished and returned its final response.

Why this matters for the exam: the exam tests the exact control flow of this loop. The correct termination condition is stop_reason == "end_turn". Common anti-patterns that appear as distractors: parsing Claude's text output for natural language signals like "I'm done", setting an arbitrary iteration cap as the primary stopping mechanism, or checking whether Claude returned a text block as a completion indicator. None of these are correct.
python — agentic loop pattern
def run_conversation(messages, tools):
    while True:
        response = client.messages.create(
            model="claude-sonnet-4-6",
            max_tokens=4096,
            tools=tools,
            messages=messages
        )

        # Append Claude's full response to history — including tool_use blocks
        messages.append({"role": "assistant", "content": response.content})

        # Correct termination condition
        if response.stop_reason == "end_turn":
            break

        # Handle tool use — extract tool_use blocks from response
        tool_results = []
        for block in response.content:
            if block.type == "tool_use":
                result = run_tool(block.name, block.input)
                tool_results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": result,
                    "is_error": False
                })

        # Append tool results as a user message and loop
        messages.append({"role": "user", "content": tool_results})

    return messages

What Goes in the Messages History

Two things must be appended to the messages list on every iteration. Getting either wrong causes a BadRequestError.

What to appendAs roleWhy
The full response.content list (not just text)assistantContains both text blocks and tool_use blocks — Claude needs both in history to reason correctly
A list of tool_result blocksuserTool results are sent as a user turn; each result references the tool_use_id from the preceding assistant message
Common mistake: appending only response.content[0].text to history instead of the full response.content list. When the response contains tool_use blocks, this drops them from history and Claude loses track of what tools it called.

Tool Results and Error Handling

When a tool call fails, return a tool_result with is_error: True and a descriptive error message. Claude receives this, understands something went wrong, and adjusts its reasoning — it may retry with different parameters, try an alternative approach, or explain the limitation to the user.

python — error handling in tool execution
try:
    result = run_tool(block.name, block.input)
    tool_result_block = {
        "type": "tool_result",
        "tool_use_id": block.id,
        "content": json.dumps(result),
        "is_error": False
    }
except Exception as e:
    tool_result_block = {
        "type": "tool_result",
        "tool_use_id": block.id,
        "content": f"Error: {e}",
        "is_error": True
    }

Multi-Agent Orchestration — Coordinator and Subagents

A single agent loop works well for focused tasks. For complex workflows — research pipelines, multi-step analysis, parallel investigations — the right architecture is a coordinator agent that delegates work to specialized subagents.

The coordinator is responsible for task decomposition, delegation, aggregating results, and deciding when enough work has been done. Subagents are specialized: one searches the web, one analyzes documents, one synthesizes findings. Each subagent only gets the tools it needs for its role.

The critical rule: subagents do not automatically inherit the coordinator's conversation history or context. Every piece of information a subagent needs must be explicitly included in its prompt. If you pass web search results to a synthesis subagent, you must include those results directly in the subagent's prompt text — it cannot reach back to the coordinator's history.

The Task Tool

Subagents are spawned via the Task tool. For a coordinator to invoke subagents, "Task" must be included in the coordinator's allowedTools configuration.

PatternHow it works
Sequential delegationCoordinator invokes one subagent at a time, passes results forward
Parallel delegationCoordinator emits multiple Task tool calls in a single response — subagents run simultaneously
Iterative refinementCoordinator evaluates synthesis output, re-delegates to search/analysis subagents with targeted queries, re-invokes synthesis until coverage is sufficient
Common coordinator mistake: overly narrow task decomposition. A coordinator asked to research "impact of AI on creative industries" that decomposes into only "AI in digital art," "AI in graphic design," and "AI in photography" will produce a report that misses music, writing, and film entirely — not because subagents failed, but because the coordinator's decomposition was too narrow. The exam tests this distinction: the subagents executed their assignments correctly; the problem was what they were assigned.

Passing Context Between Agents

When passing findings from one subagent to another, use structured data formats that separate content from metadata. Each finding should include the claim, the source URL or document name, and the publication date. This preserves attribution through synthesis — if the synthesis agent compresses findings without preserving source mappings, the final report loses the ability to cite its sources.

When two credible sources conflict on a statistic, the correct pattern is to annotate the conflict with both values and their sources, not to arbitrarily select one. The coordinator decides how to reconcile before synthesis.

Session Management — Resume, Fork, and Fresh Start

Long investigations often span multiple work sessions. Claude Code provides three mechanisms for managing session continuity, each suited to different situations.

MechanismCommandWhen to use
Named session resumption--resume <session-name>Prior context is still valid and the investigation is ongoing
Session forkingfork_sessionYou want to explore two divergent approaches from a shared analysis baseline without affecting each other
Fresh start with injected summaryNew session + structured summary in first messagePrior tool results are stale — e.g., files have changed since the last session
Exam decision rule: resuming a session is only reliable when the prior context is still valid. If you modified files after the last session, the agent's cached understanding of those files is now wrong. The correct approach is to start a fresh session and inject a structured summary of what was learned previously, then explicitly inform the agent which files changed and need re-analysis. Resuming with stale tool results is a common exam distractor.

Session forking is particularly useful for comparison tasks — evaluating two refactoring approaches, comparing testing strategies, or exploring two architectural directions from the same codebase analysis baseline. Each fork operates independently and does not affect the other.

Agent SDK Hooks — PostToolUse and Tool Call Interception

The Skilljar Claude Code course covered Claude Code hooks — pre/post tool use interceptors that run shell commands. The CCA-F exam also tests a different concept: Agent SDK hooks, which intercept tool results and outgoing tool calls in an API-level agentic application.

Two patterns matter for the exam:

Hook typeWhat it doesUse case
PostToolUseIntercepts tool results before the model processes themNormalizing heterogeneous data formats from different MCP tools — converting Unix timestamps, ISO 8601 dates, and numeric status codes into a consistent format before Claude reasons about them
Tool call interceptionIntercepts outgoing tool calls before executionEnforcing business rules — blocking a process_refund call if the amount exceeds $500, redirecting to a human escalation workflow instead
The exam meta-principle applied here: hooks provide deterministic guarantees. Prompt-based instructions ("never process refunds over $500") have a non-zero failure rate. When a business rule requires guaranteed compliance — identity verification before financial operations, policy limits on transaction amounts — use a hook, not a prompt instruction. This distinction appears across multiple exam scenarios.

The key distinction from Claude Code hooks: Claude Code hooks run shell scripts in response to file system events. Agent SDK hooks intercept API-level tool interactions in Python code, operating on the structured tool call and tool result objects that flow through the agentic loop.

Tool Design & MCP Integration

Tool descriptions, tool_choice, MCP config files, and structured error responses — Domain 2 of the CCA-F exam.

Tool Descriptions — The Primary Selection Mechanism

Claude selects tools based on their descriptions. This sounds obvious but has a non-obvious implication: when two tools have minimal or similar descriptions, Claude will misroute requests between them regardless of how clear your prompt is. The description is the contract.

A good tool description answers four questions: what does the tool do, what inputs does it expect, what does it return, and when should it be used instead of similar alternatives.

Exam scenario: production logs show an agent calling get_customer when users ask about orders, instead of lookup_order. Both tools have descriptions of one sentence ("Retrieves customer information" / "Retrieves order details"). The correct first fix is to expand both descriptions to include input formats, example queries, edge cases, and boundary explanations — not to add few-shot examples, not to build a routing layer, not to consolidate the tools. Tool descriptions are the root cause; that is the proportionate fix.

Two additional principles the exam tests:

  • Too many tools degrades reliability. Giving an agent 18 tools instead of 4-5 increases decision complexity and reduces correct tool selection. Scope each agent's tool set to what its role actually requires.
  • Generic tools cause misuse. A synthesis agent given all web search tools will attempt web searches when it should synthesize. Give agents only the tools they need, with constrained alternatives where appropriate — a verify_fact tool instead of the full search toolset.

tool_choice Configuration

The tool_choice parameter controls whether and how Claude selects tools. Three options:

ValueBehaviorWhen to use
"auto"Claude decides whether to call a tool or return textDefault — appropriate for most cases
"any"Claude must call a tool but can choose which oneWhen you need structured output and have multiple extraction schemas — guarantees a tool call without forcing a specific one
{"type": "tool", "name": "extract_metadata"}Claude must call this specific toolWhen a specific tool must run first — e.g., forcing metadata extraction before enrichment steps
Setting tool_choice: "any" is the correct answer when you need guaranteed structured output but have multiple valid extraction schemas and don't know which applies. Setting a forced tool is the correct answer when tool ordering matters for correctness.

Structured MCP Error Responses (D2.2)

When an MCP tool fails, the error response you return determines whether the agent can recover intelligently or is left guessing. A generic "Operation failed" response gives the agent nothing to work with. A structured error response gives the agent everything it needs to decide what to do next.

FieldValuesPurpose
isErrortrue / falseSignals tool failure to the agent
errorCategorytransient / validation / permission / businessTells the agent what kind of failure occurred
isRetryabletrue / falsePrevents wasted retry attempts on non-retryable errors
human-readable descriptionstringExplains the failure in terms the agent can communicate to a user

Four-Category Error Taxonomy

The errorCategory field drives recovery logic. Each category implies a different action for the coordinator:

CategoryMeaningCorrect agent response
transientTemporary failure — network timeout, service unavailableRetry with backoff; the underlying state hasn't changed
validationBad input — malformed ID, missing required fieldFix the input before retrying; retrying as-is will fail again
businessValid request, but policy blocks it — account suspended, limit exceededDo not retry; surface to the user and offer alternatives
permissionThe agent lacks authorization for this operationEscalate to a human; this is not a technical error

Two Anti-Patterns

Anti-patternWhy it's wrong
Silent suppression — returning an empty result on failureThe coordinator sees a successful search with no matches, not a failure signal. It cannot retry, escalate, or try an alternative — it assumes the query ran and found nothing.
Aborting the whole workflow on a single tool failureOne subagent's failure rarely invalidates the entire task. The correct pattern is to propagate the error with partial results and let the coordinator decide whether to proceed, retry, or escalate.
Critical distinction: an access failure (timeout, service unavailable) is different from a valid empty result (successful query with no matches). Returning an empty result as a success when the tool actually failed suppresses the error and prevents any recovery. The coordinator receives what looks like a successful search with no results, rather than a signal that the search didn't run — a fundamentally different situation.

The correct error propagation pattern: subagents handle transient failures locally with retry logic. Only errors they cannot resolve get propagated to the coordinator — along with what was attempted, any partial results, and potential alternative approaches. The coordinator then has enough context to decide whether to retry with a different query, try an alternative subagent, or proceed with partial results and annotate the gap.

Prompt Engineering & Batch Processing

Explicit criteria, few-shot examples, validation loops, and the Message Batches API — Domain 4 of the CCA-F exam.

Explicit Criteria Over Vague Instructions

The most common prompt engineering failure is vague instructions. "Be conservative" and "only report high-confidence findings" sound reasonable but give Claude no actionable definition of conservative or high-confidence. The model interprets these differently on every run, producing inconsistent results.

The correct approach is explicit categorical criteria: define exactly which issues to report and which to skip. Instead of "check that comments are accurate," write "flag comments only when the claimed behavior directly contradicts what the code actually does." The second version has a clear, testable definition.

Few-shot examples are the most effective technique for achieving consistently formatted output when detailed instructions alone produce inconsistent results. Add 2-4 targeted examples for the ambiguous scenarios — the cases where Claude's judgment is most likely to drift. Include reasoning that explains why the example output was chosen over plausible alternatives.

Validation and Retry Loops

When structured output fails validation, the correct recovery pattern is retry-with-error-feedback: send a follow-up request that includes the original document, the failed extraction, and the specific validation error. Claude uses this to self-correct.

Retries have limits. They work for format mismatches and structural errors. They do not work when the required information is simply absent from the source document — no amount of retrying will extract a field that doesn't exist in the input. Knowing when to retry versus when to accept a null value is a production consideration and an exam topic.

Error typeRetry effective?Why
Format mismatch (string where integer expected)YesClaude can reformat the same information
Structural error (nested object returned as flat)YesClaude can restructure its output
Information absent from source documentNoThe data doesn't exist — retrying asks Claude to fabricate it

Message Batches API

The Message Batches API processes requests asynchronously at 50% of the standard API cost. The tradeoff: processing takes up to 24 hours with no guaranteed latency SLA. This makes it appropriate for some workloads and unsuitable for others.

AppropriateInappropriate
Overnight technical debt reportsBlocking pre-merge checks
Weekly audit processingReal-time customer-facing responses
Nightly test generationAny workflow where a developer or user is waiting
Large document extraction batchesSequential tool-calling workflows
Hard limitation: the batch API does not support multi-turn tool calling within a single request. You cannot send a request, have Claude call a tool mid-request, and return a result — the batch processes one request/response pair. Any workflow requiring tool use must use the standard synchronous API.

Each request in a batch uses a custom_id field you define. When results come back, you match them to the original requests using this ID. When some requests fail, resubmit only the failed ones — identified by their custom_id — with appropriate modifications (such as chunking documents that exceeded the context limit).

Exam decision rule: when asked whether to use the batch API, the answer hinges on one question — does anything block on the result? If yes (pre-merge check, customer waiting, CI gate), use the synchronous API. If no (overnight report, weekly audit, nightly job), use the batch API for 50% cost savings.

Context Management & Reliability

Lost-in-the-middle, verbose tool output trimming, scratchpad files, and escalation patterns — Domain 5 of the CCA-F exam.

Context Management Patterns

As conversations grow longer and tool results accumulate, context quality degrades. Three specific effects matter for the exam:

The Lost-in-the-Middle Effect

Models reliably process information at the beginning and end of long inputs. Content in the middle receives less attention and may be omitted from the model's reasoning. This becomes a real problem in multi-agent research pipelines where findings from multiple subagents get concatenated into a single prompt.

Mitigations: place key findings summaries at the beginning of aggregated inputs, organize detailed results with explicit section headers, and avoid relying on the model to find the most important content in the middle of a long document.

Verbose Tool Output

Tool results accumulate in the conversation history and consume tokens disproportionate to their usefulness. An order lookup that returns 40 fields when only 5 are relevant to the current task wastes context on every subsequent turn.

The correct pattern is to trim tool outputs to only the relevant fields before they enter the conversation history. A PostToolUse hook is the right place to do this — it intercepts the result before the model processes it and strips irrelevant fields.

Persistent Case Facts

In multi-turn conversations, critical transactional data — order numbers, amounts, dates, customer-stated expectations — can be paraphrased away during summarization. The correct pattern is to extract these facts into a structured "case facts" block that gets included in every prompt, outside the summarized history.

python — case facts block pattern
# Extract critical facts once; include in every subsequent call
CASE_FACTS = {
    "order_id": "ORD-8821",
    "amount": 247.50,
    "customer_stated_expectation": "full refund within 3 business days",
    "issue_date": "2025-11-14"
}

system_prompt = f"""You are a customer support agent.

Current case facts (do not summarize or paraphrase):
{json.dumps(CASE_FACTS, indent=2)}

Conversation history follows.
"""

Scratchpad Files in Long Sessions

In extended codebase exploration sessions, context degrades — the model starts giving inconsistent answers and referencing "typical patterns" rather than the specific classes it discovered earlier in the session. The remedy is scratchpad files: have the agent write key findings to a file as it discovers them, then reference that file for subsequent questions rather than relying on context alone. This persists knowledge across context boundaries.

The /compact command summarizes the full conversation history while preserving the agent's learned knowledge, reducing context usage during extended sessions.

Stratified Sampling for Validation (D5.5)

When validating an extraction or classification pipeline, aggregate accuracy is a misleading metric. A system reporting 97% overall accuracy might be achieving 100% on common document types while failing at 40% on a specific type — a production-breaking error rate hidden by volume.

The correct validation pattern is stratified sampling: measure accuracy by segment (document type, field category, source format) before deciding the system is ready for automation. Aggregate accuracy is a useful headline but an insufficient basis for an automation decision.

Exam question pattern: a structured data extraction pipeline reports 97% accuracy in testing. The correct next step before automating is to break down accuracy by document type and field — not to expand the test set uniformly, not to tune the extraction prompt globally, and not to proceed to production. The 3% error rate may be concentrated in a single segment that matters.

Information Provenance in Multi-Source Synthesis (D5.6)

When a research pipeline synthesizes claims from multiple sources, each claim must carry its provenance — not just the text of the claim but its origin. Without provenance, a reader cannot assess reliability, a downstream system cannot cite sources, and conflicting statistics from different sources cannot be distinguished.

The correct pattern structures each claim as an object:

json — provenance-preserving claim structure
{
  "claim": "Q3 churn rate was 4.2%",
  "source_name": "Q3 Investor Report",
  "source_url": "https://example.com/q3-report",
  "publication_date": "2025-10-15",
  "confidence": "high"
}

When two sources report conflicting statistics, the correct behavior is to preserve both values with annotations — not to choose one, not to average them, and not to omit the conflict. Temporal data (publication dates) is particularly important: a statistic from two years ago and one from last quarter are not interchangeable, even if they describe the same metric.

Exam question pattern: two sources report different churn rates. The correct answer is to return both values with their source metadata annotated, not to select the more recent one silently, not to flag an error, and not to ask the user which to use. Preserving the conflict with annotations is itself the correct output.

Coverage Annotations in Synthesis (D5.3)

When a multi-agent system produces a synthesized output, the final result must make gaps explicit — not treat partial coverage as complete coverage. The standard pattern uses three annotation levels:

AnnotationMeaning
FULL COVERAGEAll sources for this claim were available and searched
PARTIAL COVERAGESome sources were unavailable or failed — cite which ones and why
NOT COVEREDNo source for this topic was queried — the claim is based on inference, not retrieval
Exam question pattern: a research pipeline returns a synthesis report. One subagent failed to retrieve its source. The correct behavior is to mark affected claims as PARTIAL COVERAGE and note the missing source — not to omit the claim, not to generate from context as if the source were present, and not to fail the entire pipeline.

Escalation Patterns

Knowing when to escalate to a human is as important as knowing when to resolve autonomously. The exam tests specific escalation triggers and explicitly rejects unreliable proxies.

When to Escalate

TriggerCorrect response
Customer explicitly asks for a human agentEscalate immediately — do not attempt to resolve first
Policy is ambiguous or silent on the customer's specific requestEscalate — the agent cannot make a policy decision
Unable to make meaningful progress after investigationEscalate with a structured summary of what was attempted
Case is complex but agent has a path to resolutionOffer to resolve — escalate only if customer reiterates
Unreliable escalation signals: sentiment analysis and self-reported confidence scores. A frustrated customer with a simple issue should be resolved, not escalated. An agent that is confidently wrong is the highest-risk scenario. Neither sentiment nor confidence reliably correlates with actual case complexity, which is the relevant variable. The exam explicitly tests this — sentiment-based and confidence-based escalation appear as distractors.

Nuanced Escalation: The Three-Step Pattern

When a customer expresses frustration or dissatisfaction, the correct response is not immediate escalation. The exam tests a three-step pattern:

StepActionWhy
1. AcknowledgeAcknowledge the customer's frustration explicitlyShows the agent heard them; prevents escalation of the emotional state
2. Offer resolutionOffer a concrete, actionable resolution to the underlying issueFirst expression of dissatisfaction is rarely a request for a human — it's a request for a solution
3. Escalate only if reiteratedIf the customer reiterates dissatisfaction after the offer, escalateAt that point the customer has made their preference clear
Exam question pattern: a customer says they are "extremely frustrated" with their order. The distractor answers are: escalate immediately (wrong — first expression of frustration is not an escalation trigger), ignore the emotional content and just offer the resolution (wrong — skips acknowledgment), or do nothing and ask for more information (wrong — delays resolution). The correct answer acknowledges, then offers a concrete fix, then escalates only if the customer reiterates.

Structured Handoff Summaries

When escalating to a human agent, the human does not have access to the conversation transcript. The structured handoff summary must include everything they need: customer ID, root cause, what was attempted, amounts or dates involved, and recommended action. A vague "customer is frustrated with order" handoff leaves the human starting from scratch.

Haiku remains more permissive and may still accept trailing assistant messages, but this behavior is not guaranteed across API updates and should not be relied on in production. Any request with a trailing assistant message on Sonnet or Opus returns:

BadRequestError: 400 — This model does not support assistant message prefill. The conversation must end with a user message.

The course exercise that does still work is stop sequences — stop_sequences=["5", "3, 4"] is valid on all current models and needs no changes.

Why Prefill Was a Workaround

The problem prefill solved: when asked to extract data as JSON, Claude responds conversationally — preamble, the JSON, postamble. Prefill exploited the messages array by ending with a fake assistant turn containing '{', causing Claude to continue from that point and produce only the JSON body. It worked, but it was fragile (Claude might still add text after the closing brace), semantically wrong (injecting a fake conversation turn), and caused subtle issues in multi-turn conversations where the fake turn became part of Claude's reasoning history.

The exam meta-principle: programmatic enforcement is almost always preferred over prompt-based guidance. Prefill was prompt manipulation — nudging behavior. output_config is programmatic enforcement — constraining the sampling process at the model level. When the exam asks how to guarantee structured output, the correct answer is always schema-constrained output. Prefill may appear as a distractor in answer choices.

The Modern Replacement: output_config

Anthropic's replacement for prefill-based structured output is output_config with a JSON schema. This constrains Claude at the model level to return only valid JSON matching your schema: no preamble, no markdown fences, no explanation.

python
import json
from anthropic import Anthropic

client = Anthropic()

response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1000,
    messages=[{"role": "user", "content": "Your prompt here"}],
    output_config={
        "format": {
            "type": "json_schema",          # required — specifies format type
            "schema": {                     # sits directly inside "format", not wrapped
                "type": "object",
                "properties": {
                    "field_name": {"type": "string"},
                    "count":      {"type": "integer"},
                    "items":      {"type": "array", "items": {"type": "string"}}
                },
                "required": ["field_name", "count", "items"],  # names must match exactly
                "additionalProperties": False  # required by the API on all object types
            }
        }
    }
)

data = json.loads(response.content[0].text)

Arrays of Objects: Nested Schema Pattern

When a field contains a list of structured items — each with multiple properties — use an array of objects. Each item in the array is itself an object with its own properties and required fields.

python — nested array schema
"kpis": {
    "type": "array",
    "items": {
        "type": "object",
        "properties": {
            "current": {"type": "string"},
            "target":  {"type": "string"}
        },
        "required": ["current", "target"],
        "additionalProperties": False
    }
}
additionalProperties: False applies to every object in the schema, including nested objects inside array items. Omitting it on a nested object causes a 400 error even if the top-level object has it set correctly.

A full working example using this pattern is in consulting_notes_extractor.py. It extracts structured findings (client, priority, actions, problems, KPIs) from unstructured meeting notes and includes six tests in test_consulting_notes_extractor.py. The original course notebook is preserved as 004_structured_output.ipynb.

Prompt Evaluation — generate_dataset and grade_by_model Prefill → output_config

Second instance of this pattern: The Skilljar "Building with the Claude API" course notebook 001_prompt_evals.ipynb uses the same deprecated prefill technique in both generate_dataset and grade_by_model: wrapping a response in a ```json code fence and cutting it off with a stop sequence. This fails on Sonnet and Opus for the same reason: the API no longer accepts a trailing assistant message on those models.

The deprecated pattern from the course:

deprecated — do not use 
# Broken on Sonnet and Opus — prefill hack
messages = []
add_user_message(messages, prompt)
add_assistant_message(messages, "```json")   # fake assistant turn
text = chat(messages, stop_sequences=["```"])    # cut before closing fence
return json.loads(text)

The output_config Replacement

The corrected generate_dataset function uses output_config directly in the client.messages.create() call. Note that the schema top-level type is "array", not "object" — the API returns a list of task objects rather than a single object. Arrays can be the top-level schema type when your output is inherently a collection.

generate_dataset — corrected 
import json

def generate_dataset():
    prompt = """
Generate 3 evaluation tasks for prompts that produce Python, JSON, or Regex
for AWS-related use cases. Each task should be solvable with a single function,
object, or expression.
"""
    response = client.messages.create(
        model="claude-haiku-4-5",
        max_tokens=1000,
        messages=[{"role": "user", "content": prompt}],
        output_config={
            "format": {
                "type": "json_schema",
                "schema": {
                    "type": "array",           # top-level is a list, not an object
                    "items": {
                        "type": "object",
                        "properties": {
                            "task": {"type": "string"}
                        },
                        "required": ["task"],
                        "additionalProperties": False
                    }
                }
            }
        }
    )
    return json.loads(response.content[0].text)
Where output_config belongs: output_config goes in the specific client.messages.create() call where structured JSON is needed — not in a general-purpose chat() helper. The chat() helper stays generic. Only the function that contracts with the API for a particular shape carries output_config. This is the same pattern used in consulting_notes_extractor.py.
Why the grader notebook may still run: The supplied 001_prompt_evals_grader.ipynb uses claude-haiku-4-5, which remains more permissive about trailing assistant messages than Sonnet or Opus. The notebook may run successfully as provided. This is not a reason to keep the pattern — Haiku's permissiveness is not guaranteed across API updates. Use output_config for any structured output that needs to be stable.

The repo preserves the corrected notebook as 001_prompt_evals.ipynb.

Text Editor Tool — Tool Name Mismatch

Course notebook bug — infinite loop: The Skilljar "Tool Use with Claude" course notebook 005_text_editor_tool.ipynb dispatches tool calls using the deprecated tool name "str_replace_editor" in run_tool, but registers the tool with the current name "str_replace_based_edit_tool" in get_text_edit_schema. These names never match. Every tool call returns is_error: True, Claude retries, and the while True loop never breaks — the kernel appears stuck and the cell must be interrupted manually.

The mismatch in the original notebook:

cell 3 — deprecated, do not use 
# run_tool dispatches on the old name — never matches
if tool_name == "str_replace_editor":   # ← wrong

# cell 4 registers the tool with the current name
"name": "str_replace_based_edit_tool"   # ← what Claude actually calls

The Fix

Update the if condition in run_tool to match the name the API actually uses for text_editor_20250728. The tool name is fixed by Anthropic and cannot be changed.

cell 3 — corrected 
def run_tool(tool_name, tool_input):
    if tool_name == "str_replace_based_edit_tool":   # matches the registered name
        command = tool_input["command"]
        # ... rest of dispatch unchanged
Why the loop hangs: When run_tool raises an exception, run_tools catches it and returns a tool_result block with is_error: True. Claude receives the error, says "let me try again," and calls the same tool — which fails again. Because stop_reason stays "tool_use", the while True loop never reaches its break condition. The fix is the same principle as always: the name in your dispatch must exactly match the name Claude uses when calling the tool.

The notebook also used the deprecated model string claude-sonnet-4-5. Update to claude-sonnet-4-6. The corrected notebook is preserved as 005_text_editor_tool.ipynb in the repo.

Web Search Tool — Demo Question Produces No Search

Content gap — no error, but the lesson does not demonstrate what it claims: The Skilljar "Tool Use with Claude" course notebook 006_web_search_complete.ipynb asks "What's the best exercise for gaining leg muscle?" This is stable knowledge Claude answers from training data. No web search fires. The ServerToolUseBlock and WebSearchToolResultBlock response structure the lesson exists to demonstrate never appears in the output.

Claude decides whether to search based on whether the question requires current information. Stable knowledge questions — best practices, definitions, general advice — are answered from training data regardless of whether a search tool is registered. The fix is to ask a question that signals recency.

cell 4 — original, produces no search 
# Claude answers from training data — no ServerToolUseBlock in response
add_user_message(messages, "What's the best exercise for gaining leg muscle?")
cell 4 — corrected, forces a live search 
# "latest" signals recency — Claude searches rather than answering from memory
# allowed_domains: ["nih.gov"] already in the schema, so the search stays scoped
add_user_message(messages, """
    What are the latest NIH recommendations on exercise for cardiovascular health?
""")
What the full response looks like when a search fires: The response content array contains a ServerToolUseBlock (showing the query Claude used), a WebSearchToolResultBlock (the search results), and a final TextBlock (Claude's answer with citations). The server_tool_use field in response.usage will show a non-zero web_search_requests count. If you only see a single TextBlock and server_tool_use: None, no search fired — rephrase the question to require current information.

The notebook also used the deprecated model string claude-sonnet-4-5. Update to claude-sonnet-4-6. The corrected notebook is preserved as 006_web_search_complete.ipynb in the repo.

Extended Thinking — budget_tokens → Adaptive Thinking

Deprecated API pattern: The Skilljar "Features of Claude" course notebook 001_thinking_complete.ipynb uses thinking={"type": "enabled", "budget_tokens": N} — the fixed token budget thinking API. This is deprecated on Sonnet 4.6 and Opus 4.6, and removed entirely on Opus 4.7 and later. Requests using type: "enabled" on Opus 4.7+ return a 400 error. The RedactedThinkingBlock the notebook was designed to demonstrate no longer exists as a discrete block type on current models.

The deprecated pattern from the course:

deprecated — do not use on 4.6+ 
# Broken on Opus 4.7+ — returns 400 error
# Deprecated on Sonnet/Opus 4.6
params["thinking"] = {
    "type": "enabled",
    "budget_tokens": thinking_budget,   # fixed token budget — removed
}

The Adaptive Thinking Replacement

Adaptive thinking replaces the fixed token budget with an effort level. Claude decides if and when to think based on problem complexity — a simple question may produce no thinking block at all. Use a genuinely complex problem to reliably observe a ThinkingBlock in the response.

corrected — adaptive thinking 
# Adaptive thinking: Claude decides when to think based on complexity
# effort: "low" | "medium" | "high" | "max"
params["thinking"] = {
    "type": "adaptive",
    "effort": "high",
}

# Extract thinking content from the response
for block in response.content:
    if block.type == "thinking":
        print(block.thinking)   # ThinkingBlock — not RedactedThinkingBlock
Why RedactedThinkingBlock no longer appears: RedactedThinkingBlock was produced by the old type: "enabled" API when Claude's reasoning was withheld for safety reasons. The adaptive thinking API replaced this entirely. With type: "adaptive", Claude either produces a ThinkingBlock with summarized reasoning or produces no thinking block at all. There is no equivalent to RedactedThinkingBlock in the current API.

thinking.type: "adaptive" + effortCurrentRequired on Opus 4.7+; recommended on all 4.6 models
